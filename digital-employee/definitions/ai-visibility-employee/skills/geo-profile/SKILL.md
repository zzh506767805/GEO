# 建档和监测设置

## 整体流程

这个员工的工作分五步，本 Skill 负责前三步：

| 步 | 做什么 | 用哪个 Skill | 要等商家吗 |
| --- | --- | --- | --- |
| 1 | 首次获取信息：从店铺后台读资料 | 本 Skill | 不用 |
| 2 | 写差异点、出题 | 本 Skill | 不用 |
| 3 | 开通工作台、固定到客户端页签，请商家确认问题，确认后开始第一次体检 | 本 Skill → `geo-check` | **要**：商家明确同意才体检 |
| 4 | 出第一份报告、写第一篇内容、汇报结果，问他要不要开启每周体检 | `geo-weekly`、`geo-content` | 开启每周体检要他同意 |
| 5 | 每周：重读资料、体检、出报告、写建议和内容，让商家去发 | `geo-check` → `geo-weekly`、`geo-content` | 内容发出去之前要他确认 |

本 Skill 管两样东西：

- **店铺资料**：从店铺后台读来的店名、门店、营业时间、商品、小程序。体检时拿它核对 AI 说得对不对，替商家写内容也只用它里面的事实。它是你的工作底稿，**不在工作台上展示**：这些是商家自己在后台维护的，抄一份给他看只会抄不全。
- **监测设置**：这家店的差异点、每周替商家问 AI 的问题、和哪几家同类店比，以及商家告诉你的、后台里没有的几样信息（他的公众号、抖音号、写作要求）。商家在工作台的“监测设置”页上看得到。

**不去搜商家在别的平台的账号。** 搜到的账号认不准，还要商家一个个确认，收益不值这一步。商家自己说了公众号、抖音号，再记下来。

监测设置每改一次，都要同步一次工作台（同步的命令在 `geo-workbench` Skill 里，下面用 `publish` 指代）：

```bash
python3 "$YOUZAN_AGENT_SESSION_WORKSPACE/.claude/skills/geo-workbench/scripts/geo_report.py" publish
```

## 开始前

- 本 Skill 的脚本：

```bash
python3 "$YOUZAN_AGENT_SESSION_WORKSPACE/.claude/skills/geo-profile/scripts/geo_state.py" status
```

  下文表格里写的 `geo_state.py ...`、`set-facts`、`show` 都是这个全路径的简写，执行时写全。

- 入参先写成 JSON 文件，放在会话临时目录 `$YOUZAN_AGENT_SESSION_TEMP/geo/` 下，再用 `--file` 传入。
- 先执行 `status`，按结果决定从哪一步接着做：

| `status` 的结果 | 接着做 |
| --- | --- |
| `exists: false` | 从第 1 步开始建档 |
| `firstCheckPending: true` | 还在等商家确认（第 3 步）。不重复建档、不体检；商家这次说的是同意，就按第 3 步往下走，否则提醒他看一眼问题 |
| `lastRun` 为空，`firstCheckPending: false` | 商家确认过了、还没体检：按 `geo-check` 跑第一次体检 |
| `lastRun` 不为空、`schedule` 为空 | 第一份报告出了、还没问过每周体检：按 `geo-weekly` 的“开启每周体检” |
| 其他 | 已经在每周的节奏里，商家要改设置就看下面的“修改” |

- `status` 里的 `workbench` 是工作台的情况：`pending` 不为空，说明有变化还没同步上去，做完手上的事要 `publish`。
- 脚本返回 `ok: false` 时，按 `error` 修正后重试。存档只通过脚本改。

## 哪些要商家确认，哪些不用

| 信息 | 从哪来 | 要不要商家确认 |
| --- | --- | --- |
| 店名、门店、营业时间、商品、小程序 | 店铺后台 | **不用**。那是他自己填的，以后台为准 |
| 别的叫法、后台里没有的门店（比如已经关掉的旧店） | 你推断的或从别处看到的 | **要**。可能认错 |
| 他的公众号、抖音号、写作要求 | 他自己说的 | 不用，记的时候加 `--confirmed-by-merchant` |
| 差异点、问题、同类店 | 你写的 | 第 3 步请他看一眼问题；之后他随时可以改 |

- 从店铺后台读到的资料，`set-facts` 时写 `"from": "backend"`。这样不用等商家确认，就可以替他写内容。**漏写 `from` 会被当成从公开信息整理的**，脚本会在 `warnings` 里提醒。
- 查不到店铺后台、资料是从公开信息里整理的，写 `"from": "public"`。这时整份资料都要商家看过才算数，确认之前脚本不让你登记内容。
- `status` 里的 `pendingConfirm` 为 true，说明有你另外记下的信息还没经过商家确认，`toConfirm` 里列着具体是哪几样。没确认的信息不能写进内容。

## 第 1 步：首次获取信息

初始化这一轮只做第 1 到第 3 步：不向 AI 提问，不写内容。

### 判断是本地门店还是电商

通过 `youzan-data-analyst` Skill 查店铺名称、主营类目、店铺类型、门店列表和配送方式。

- 有线下门店、顾客主要到店或同城下单：`local`（本地门店）。
- 没有门店，或主要全国发货：`ecom`（电商）。
- 两样都有：按主要收入来源选一套，从这一套的 10 道题里换出 2 道，按另一套的配比出。

然后只读对应的一份说明：`references/segment-local.md` 或 `references/segment-ecom.md`。它规定了资料里多记什么、怎么出题。

### 读店铺资料

能从店铺后台查到的不要问商家。查不到的字段留空，**禁止推测或编造**；留空不会出错，写错会让后面的核对全错。

| 字段 | 内容 | 来源 |
| --- | --- | --- |
| `brand` | 店名、品类、城市；`aliases` 是别的叫法（英文名、简称），属于要确认的 | 店铺后台；别名是你推断的 |
| `stores` | 每家门店的名称、地址、营业时间、电话、状态（在营 / 已搬迁 / 已关闭） | 后台的门店 `source` 写“有赞后台”；从别处看到的写实际来源 |
| `products` | 热销和核心商品的名称、规格、价格带、产地（电商必填，最多 10 个） | 店铺后台 |
| `buyEntry` | 小程序名称、店铺链接 | 店铺后台 |
| `edges` | 和同类店不一样的地方，见第 2 步 | 你写的 |
| `channels` | 他的公众号、抖音号 | 商家说了才填 |
| `writingRules` | 口吻、不用的词、每篇必须带的信息 | 商家说了才填 |

能查到商品评价（`youzan-item` Skill）时，顺手摘几句顾客的原话，出题时照顾客的说法写。查不到就跳过，不影响往下做。

### 要用的能力不可用时

哪个不可用，按下表降级，接着往下做：

| 不可用的能力 | 怎么办 |
| --- | --- |
| `youzan-data-analyst`（查店铺资料） | 按公开信息整理资料，`from` 写 `public`；第 3 步请商家连资料一起看 |
| `youzan-item`（查商品评价） | 跳过，只用热销商品和价格带 |
| 问 AI 能力（体检） | 第 1 到第 3 步照常做完，告诉商家暂时不能体检 |

## 第 2 步：写差异点、出题

### 写差异点

先写 1 到 3 条**这家店和同类店不一样的地方**（`edges`）。不带店名的问题都要挂在差异点上出，不能挂在“这家店卖什么”上：按商品清单出的题，同类店个个都能答，AI 没有理由提到他。

- 差异点是顾客能感受到的区别：价格（清仓价、临期折扣）、规格（体验装、小包装）、品类组合（母婴和零食一次买齐）、地段（这一片唯一一家）、服务（30 分钟送到）。
- 依据写在 `basis` 里，只用查得到的：热销品、价格带、门店位置、评价原话。没有依据的写“推测”。
- 每条 30 个字以内，例如“大牌母婴体验装，价格比正装低一半”。
- 实在找不出差异点，就退到地段：门店所在街道附近同类店少，本身就是差异点。

差异点会显示在工作台的“监测设置”页上，商家说不对就改。

### 出题

按客群说明里的配比出 10 个不带店名的问题和 2 个带店名的问题。

- 每道题写上 `audience`（替谁问，12 个字以内，例如“附近带娃的家长”）和 `worry`（他在意什么）。这两项是出题时顺手写的一句话，不用先归纳顾客类型再凑题。
- 用顾客的口气和他会用的词写，把他在意的事写进问题里。例如控糖的人不会问“哪家面包店好”，会问“有没有适合控糖的人吃的面包店”。
- 不带店名的问题里不能出现店名和别名，否则结果虚高，脚本会拒绝。
- 多出具体的问题：具体街区、具体单品、具体场合、具体价位。“全国哪个牌子好”这类大问题，小店赢不了，最多留 1 个当参照。

每道不带店名的题出完，按下面四条过一遍，过不了的改掉：

| 检查 | 过不了的样子 | 改成 |
| --- | --- | --- |
| 挂在哪条差异点上 | “杭州有没有小程序下单、当天送到的社区小店？”（什么店都能答） | 换成能体现差异点的问法，或者删掉 |
| AI 会列几家、这家店算不算好答案 | 标准答案是盒马、美团、山姆这类平台或连锁 | 加上这家店才有的条件（清仓价、体验装、某条街），让答案只剩三五家 |
| 一道题只有一个需求 | “哪里能买到便宜的洞洞鞋和轻奢清仓包？” | 拆成两道，或者只留一个 |
| 顾客真会这么打字 | “正装之外的体验装和尝鲜装”“银耳罐头、冰激凌这类耐放的吃食”（从商品清单拼出来的） | 换成顾客的说法：“哪里能买到大牌尿裤的试用装？” |

- 渠道题（小程序下单、配送、自提）单独问一定输给平台，要和差异点或地段绑在一起问，例如“留下附近有没有能小程序下单、到店自提的折扣店？”。
- 带店名的 2 个固定为“某某怎么样”和“某某在哪、几点开门、有什么招牌”。
- 同类店这一步先不定，第一次体检后从 AI 实际提到的店里挑。

### 写入

```bash
python3 "$YOUZAN_AGENT_SESSION_WORKSPACE/.claude/skills/geo-profile/scripts/geo_state.py" init --segment local --brand "店名"
python3 "$YOUZAN_AGENT_SESSION_WORKSPACE/.claude/skills/geo-profile/scripts/geo_state.py" set-facts --file "$YOUZAN_AGENT_SESSION_TEMP/geo/facts.json"
python3 "$YOUZAN_AGENT_SESSION_WORKSPACE/.claude/skills/geo-profile/scripts/geo_state.py" set-questions --file "$YOUZAN_AGENT_SESSION_TEMP/geo/questions.json"
```

`facts.json`：

```json
{
  "from": "backend",
  "segment": "local",
  "brand": {"name": "", "aliases": [], "category": "", "city": ""},
  "edges": [{"text": "", "basis": "热销品"}],
  "stores": [{"name": "", "address": "", "hours": "", "phone": "", "status": "在营", "source": "有赞后台"}],
  "products": [{"name": "", "spec": "", "priceRange": "", "origin": ""}],
  "buyEntry": {"miniProgram": "", "shopUrl": ""}
}
```

`questions.json`（`kind` 为 `open` 表示不带店名，编号用 q01 起；`brand` 表示带店名，编号用 b01 起）：

```json
[
  {"id": "q01", "kind": "open", "tag": "地段", "text": "", "audience": "", "worry": ""},
  {"id": "b01", "kind": "brand", "tag": "口碑", "text": ""}
]
```

脚本返回的 `warnings` 要处理：能补的补上，补不了的在第 3 步告诉商家。

## 第 3 步：开通工作台、固定页签，请商家确认

### 开通工作台

```bash
python3 "$YOUZAN_AGENT_SESSION_WORKSPACE/.claude/skills/geo-workbench/scripts/geo_report.py" publish
```

这时还没有体检结果，工作台首页是“现在到哪一步了”，“监测设置”页上是差异点和问题。输出里 `firstTime: true`，`pageUrl` 就是工作台的链接，以后一直是这一个。

### 固定到客户端页签

开通工作台后，按 `geo-workbench` 的 `references/tabs.md` 把工作台固定到客户端。

### 请商家确认，然后停下来等

一条消息，六行以内：

1. 识别到的店铺：店名、本地门店还是电商、主营什么。
2. 你理解的这家店的特点（差异点），一两句。告诉他问题都是按这个出的，不对就说。
3. 两三个代表问题，完整的在工作台的“监测设置”页。给链接；页签固定成功了，再说“上面加了一个「AI 曝光工作台」页签，还没看到的话切到别的页签再切回来”。
4. 资料是从公开信息整理的（`from` 为 `public`）时，请他连资料一起看一眼。
5. 只问一次：方向是否合适，是否开始第一次体检，大约十分钟出结果。

到这里停下来，不调用 `geo-check`，不问 AI。

- 商家要改差异点或问题：按下面的“修改”改好、`publish`，再问一次要不要开始。改信息本身不代表同意体检。
- 商家明确说“可以”“开始吧”“确认，开始”或类似的话，执行：

```bash
python3 "$YOUZAN_AGENT_SESSION_WORKSPACE/.claude/skills/geo-profile/scripts/geo_state.py" confirm-monitoring
```

  然后按 `geo-check` 跑第一次体检，接着按 `geo-weekly` 的“第一份报告”走第 4 步。
- 资料是从公开信息整理的，商家同时说了“资料没问题”：再执行一次 `confirm`，之后才能替他写内容。

## `set-facts` 是合并，不是覆盖

`set-facts` 只改你传了的部分：

- **没传的字段保持原样。** 例如只传 `brand`、`stores`、`products`、`buyEntry`，别名、差异点、他的公众号和抖音号、写作要求都会留着。
- `brand`、`buyEntry`、`channels`、`writingRules` 按字段合并：`{"channels": {"douyin": "某某"}}` 只改抖音号。
- `stores` 里全是后台的门店（`source` 是“有赞后台”）时，你另外记下的门店（比如已经关掉的旧店）会保留；传了非后台的门店，就以这次传的整份门店为准。
- 要删掉某一项，就把它**传成空值**，例如 `{"channels": {"douyin": ""}}`。
- 输出里的 `kept` 列出这次原样保留下来的字段，看一眼是不是你想要的。
- 只有要从头重写整份资料时才加 `--replace`：没传的字段会全部清空。

## 每期体检前：重读一遍店铺资料

每周体检之前，重新从店铺后台读一遍资料，用 `set-facts` 写回：只传后台读得到的那几样（店名、品类、城市、门店、商品、购买入口），带上 `"from": "backend"`。你另外记下的那几样不用传，脚本会保留。营业时间改了、多了一家店，这样才能跟上。从后台重读带来的变化不用商家再确认。

## 修改

商家的话很多是从工作台上复制过来的。工作台和报告上问题的编号是 Q1、Q2、B1 这样，对应 `q01`、`q02`、`b01`。

| 商家说 | 做法 |
| --- | --- |
| “把 Q3 换一个问法”“把 Q3 删掉”“加一道题：……” | `show --part questions` → `set-questions`；提醒商家：改了问题原文，之前的数就不能和之后的比了。然后按 `geo-check` 只重跑改过、新加的题，重新算分（删掉的题不用重跑，重新算分时这一期就不再算它）→ `publish` |
| “同类店换成……” | `set-rivals --file <文件>`（`[{"name": "", "aliases": []}]`，最多 5 家），按 `geo-check` 重新算分 → `publish` |
| “我的公众号叫……”“我的抖音号是……” | 只传这一项，例如 `{"channels": {"wechatOfficial": "某某"}}`，`set-facts` 时加 `--confirmed-by-merchant`。然后按 `geo-check` 重新算分（统计“本店内容被引用”会用到）→ `publish` |
| “可以，开始吧”“确认，开始”（还在第 3 步等确认时） | 按第 3 步：`confirm-monitoring` → 第一次体检 |
| “这些信息没问题，确认”（已经体检过，确认别名、旧门店这类你另外记下的信息） | `confirm` → `publish` |
| “这个抖音号不是我的”“那家店早就关了” | 先 `show --part facts` 看清现在记的是什么。抖音号不对就传空值（`{"channels": {"douyin": ""}}`）；门店要传改好的整份 `stores`。加 `--confirmed-by-merchant` → `publish` |
| “我们家主要是……便宜”“我们的特点是……”“这个特点不对” | 传改好的整份 `edges`，`set-facts --confirmed-by-merchant`；挂不上新差异点的问题提出改法，他同意再改 → `publish` |
| “每周体检停掉”“先别每周跑了” | 按 `geo-weekly` 的“开启每周体检”里关掉的做法 |
| “写东西不要用某个词”“口吻随意一点” | 只传 `writingRules` 里要改的那一项（`bannedWords` 要传完整的列表），`set-facts --confirmed-by-merchant` → `publish` |
| “营业时间是……”“我们搬到……了” | 这是店铺后台里的资料。按他说的先记下（`--confirmed-by-merchant`），并提醒他把店铺后台也改掉，否则下一期重读时又会变回去 |

你自己改资料时不要加 `--confirmed-by-merchant`。要确认的那部分变了，脚本会自动标成“等商家确认”。

改完以后告诉商家哪里更新了，给“监测设置”页的链接。

## 对外表达

- 只说业务语言：店铺资料、你家的特点、问题、同类店、体检、报告、工作台。
- 不向商家展示脚本、命令、字段名、文件路径和内部报错。
